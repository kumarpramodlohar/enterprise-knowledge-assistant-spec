# 013 Authentication and Authorization Service Extraction — Specification

**Status:** Owner selected the target boundary and initial design directions on 2026-11-07. Initial Go components and a loopback-only synthetic test server exist; detailed design, a production-ready service, integration, and cutover remain incomplete. The current implementation and existing approved behavior remain in force until a replacement is approved and verified.
**Target repository:** `enterprise-knowledge-auth` (available as a sibling Git repository; experimental local testing only).
**Related:** [DEC-001 and DEC-013](../../docs/implementation/product-decisions.md), [OIDC specification](../004-oidc-authentication/spec.md), [API contract](../001-project-foundation/api-contract.md), [backlog](../../docs/implementation/Implementation_Backlog_v2.md).

## 1. Problem and goal

Authentication and collection authorization are currently coupled to the Java application. Separate identity and authorization policy responsibilities into a Go service without interrupting sign-in or weakening the protection of documents, retrieval, model context, or citations. Keep Keycloak as the identity provider.

## 2. Scope and ownership

| Concern | Current implementation | Target responsibility |
|---|---|---|
| Identity provider | Keycloak for OIDC; local Spring Basic for development | Retain Keycloak and initially preserve current local Basic authentication; a safe replacement requires separate approval. |
| Login, callback, session and sign-out UI | React frontend and `oidc-client-ts` | Initially retain direct Keycloak PKCE sign-in and existing browser session behavior. |
| Token validation | Spring Security resource server | Java backend validates the caller's identity; the auth service validates identities appropriate to its own interfaces. Exact token audiences and trust paths remain open. |
| User provisioning, application roles and collection grants | Java backend and PostgreSQL `app_users` / `collection_grants` | Go auth service owns these policies, initially in an auth-owned schema on the existing PostgreSQL deployment with separate least-privilege access. Migration and reference integrity require detailed design. |
| Policy decisions | Java `AccessService` reads roles and grants | Go auth service supplies permission checks and bounded permitted-collection lists via an internal HTTPS/JSON API; backend calls use mTLS. Exact API and failure behavior require detailed design. |
| Protected resources and enforcement | Java document/chat services | Java remains the enforcement point for document operations, metadata, retrieval, citations, and AI-provider context. Client UI flags never grant access. |
| Collections, documents, chunks and vectors | Java backend and PostgreSQL | Remain with the knowledge backend. Collection lifecycle integration with auth-owned grants must be designed. |
| `/api/v1/me` | Java backend exposes role and collection scopes | Initially retain the Java endpoint and its client-visible contract; the backend obtains target policy from the auth service. |

This feature does not authorize removal of login screens, server-side enforcement, Keycloak, or the existing implementation before cutover. It does not approve multi-tenancy, tenant switching, or new administration features.

## 3. Functional requirements

- FR-1: The target auth service is implemented in Go in its own repository and owns application identity provisioning, roles, collection grants, and authorization policy decisions.
- FR-2: Preserve Keycloak OIDC sign-in and the existing user-facing session behavior unless a separate change is explicitly approved. Browser credentials and tokens must not be logged or persisted in application web storage.
- FR-3: Retain `ADMIN` and `MEMBER` roles and `READ`/`MANAGE` semantics; a newly provisioned OIDC user starts as `MEMBER` with no collection grants.
- FR-4: The knowledge backend independently validates caller identity and enforces the auth service's authoritative policy before protected document operations, retrieval, citations, or supplying protected context to an AI provider.
- FR-5: Auth-service failures, invalid responses, invalid identity, or an untrusted caller must not result in granting access. Invalid caller credentials retain the appropriate authentication failure; an inability to obtain an authorization decision must be surfaced as a safe service failure, not falsely reported as successful access or an ordinary insufficient-evidence result.
- FR-6: Inaccessible and nonexistent resources remain indistinguishable as 404. Unauthorized requests must not disclose resource names, metadata, contents, citations, or protected context.
- FR-7: Preserve the `/api/v1/me` response and existing authentication/error semantics for clients until a replacement contract and coordinated transition are approved.
- FR-8: Migrate existing users, role assignments, grants, and collection references without unauthorized widening or loss of access. Establish an authoritative source and consistency rules for each migration phase.
- FR-9: Remove superseded auth-specific implementation from existing repositories only after the replacement is operational, migration and integration checks pass, and rollback is ready. Keep necessary frontend sign-in/session UX, backend identity validation, and server-side enforcement.
- FR-10: Preserve historical task/test evidence; reassign auth-only outstanding work and split mixed backlog items without removing their non-auth portions or release dependencies.
- FR-11: Request fresh policy information for each protected operation without caching authorization decisions. This is a point-in-time decision; handling of revocation during an in-flight operation requires a detailed design and verification.
- FR-12: Only an authorized, mTLS-authenticated Java backend may assert a subject after authenticating the user; the auth service must reject subject assertions from browsers and other unauthorized callers. Apply the same trust boundary to local Basic.
- FR-13: Recheck authorization before sending protected context to an AI provider and before returning protected citations or content. Specify and test the remaining race guarantees; a recheck alone does not ensure instantaneous revocation.
- FR-14: The internal API is versioned and supports provisioning, permission checks, and paged scope results. Scope results must be complete and consistent; if a configured limit is exceeded or completeness cannot be established, fail closed rather than silently truncating `/api/v1/me` or a protected operation.
- FR-15: For auth-service timeouts, unavailability, or invalid responses, return a safe 503; start with a configurable two-second total deadline and at most one retry for explicitly idempotent reads. Keep inaccessible-resource denials non-disclosing as 404.
- FR-16: Use deployment-managed CA and client/server certificates, support rotation, reject expired/untrusted/unknown client identities, and use a separate local-development CA with private keys outside Git. Never fall back to unauthenticated transport in production.
- FR-17: Use separate least-privilege runtime and migration roles. Preserve a cross-schema grant-to-collection foreign key with cascading grant deletion; verify collection lifecycle and database privileges.
- FR-18: Freeze policy writes during migration/cutover and reconcile users and grants. Rehearse rollback and reverse-reconcile all post-cutover changes under a write freeze before restoring the former authority; cutover requires separate approval.
- FR-19: For paged authorized scopes, return a global policy revision with the first page and atomically check it against scope-affecting changes on each subsequent page. Changes to roles, grants, or collection lifecycle that affect scopes, including cascading grant deletion, invalidate ongoing reads for all users. On a mismatch, discard all accumulated pages; a complete read may restart within the existing deadline and retry limit. If a complete, consistent result cannot be obtained, fail closed with a safe 503. Start a fresh read for each protected operation.
- FR-20: Initially configure the maximum authorized scope to 10,000 distinct collection IDs per user across readable and manageable scopes. A collection present in both counts once. The limit is configurable; exceeding it must fail closed with a safe 503 without returning a truncated scope.
- FR-21: Provide separate internal operations to provision or resolve an authenticated user, check a requested permission for a collection, and read the user's role and paged collection scopes. Selected paths, field shapes, pagination and error categories are specified below; remaining contract details require further review.
- FR-22: Paged scope responses contain one entry per authorized collection with its effective `READ` or `MANAGE` permission, the user's role, the global revision, and a continuation cursor when more pages exist. `MANAGE` includes `READ`. For `/api/v1/me`, Java reconstructs the existing readable list from all entries and the manageable list from `MANAGE` entries. `ADMIN` scopes include all applicable collections and remain subject to the configured scope limit.
- FR-23: A successfully evaluated internal permission check returns an explicit `ALLOW` or `DENY`. Malformed requests, unknown permission values, service failures, and invalid responses are errors, not decisions; inability to obtain a decision fails closed with a safe 503. Genuine denials for protected resources remain non-disclosing 404s. The backend must independently establish resource existence and collection ownership; `ALLOW` alone does not establish either.
- FR-24: Use stateless, integrity-protected continuation cursors, verified on every page and bound to the authenticated backend caller, asserted user, query, and global revision. Atomically check the current revision independently of cursor verification. Invalid, tampered, or mismatched cursors fail closed; a cursor does not cache or grant authorization. Signing does not provide confidentiality: do not expose or log sensitive cursor contents. Key management, expiry, and error mapping require further review.
- FR-25: Maintain the global revision in PostgreSQL using database triggers for all scope-affecting role, grant, and collection changes, including cascaded grant deletion. Each change and its revision update must commit or roll back together. Read the revision, role, and scope page from one consistent database snapshot, reject mismatched revisions, and never combine pages across revisions. Trigger privileges, migrations, concurrency, and lifecycle mechanics require security review.
- FR-26: Authenticate backend client certificates and authorize their service identity by exact match of a URI Subject Alternative Name against a deployment-configured allowlist. Reject invalid or expired certificates and missing or unknown identities. Certificate rotation may retain the same service identity. The backend must validate the auth service's server certificate and expected server identity. Certificate issuance, revocation, and local setup require further review.
- FR-27: Distinguish OIDC identities by validated issuer and subject, and local identities by a separately configured local namespace and username. Only the authenticated and authorized backend may assert these identities after authenticating the user; browser-supplied identity assertions are not trusted. Preserve the public `/api/v1/me` subject. Migrate users and grants using explicitly verified mappings; stop for review on ambiguity rather than silently merging accounts or transferring grants. This does not approve additional issuers or multi-tenancy.
- FR-28: Use freeze-and-copy migration: pause policy writes, take a consistent snapshot of existing users and grants, map every identity explicitly, copy to the auth-owned schema, and reconcile every role and grant with the source. Stop on ambiguous identities, missing collections, conflicts, or mismatches. Java remains the policy authority until verification and separate cutover approval; do not allow competing policy-write authorities. Resume policy writes only after the selected authority is established. The runbook, rollback, and outage plan remain to be reviewed.
- FR-29: During the migration write freeze, block first-time user provisioning and scope-affecting collection changes in addition to policy writes. Existing authenticated users may continue read-only access only while the current authority can enforce fresh authorization; otherwise fail closed. Requests requiring a blocked write receive a safe temporary service-unavailable response without partial changes. The precise affected operations and messages require review.
- FR-30: The initial emergency response to a compromised backend client certificate removes the affected URI SAN from the allowlist and terminates existing connections for that identity. This blocks all certificates sharing that identity. Restore service using a new URI SAN identity and new certificate while keeping the compromised identity blocked. Re-enable the old identity only after separately verifying that the compromised certificate can no longer authenticate. Certificate lifetimes, propagation deadlines, in-flight requests, operational procedures, and server-certificate compromise handling require further review.
- FR-31: During rollback, an identity collision, unmappable user, missing collection, or role/grant mismatch blocks the authority switch. Keep policy writes frozen, resolve the conflict, and rerun reverse reconciliation, except when invoking the controlled emergency abort in FR-55. Fail closed for operations that cannot be safely authorized; never drop or broaden grants merely to complete rollback. The detailed rollback runbook requires review.
- FR-32: Grant the auth runtime database role read-only access to the backend-owned collection ID column needed for complete `ADMIN` scopes, not document content or other collection fields. Keep policy data in the auth-owned schema and migration privileges separate. Exact PostgreSQL grants, trigger privileges, and ownership require security review.
- FR-33: Expose backend-only versioned JSON operations `POST /internal/v1/users/resolve` for authenticated identity resolution and eligible OIDC provisioning, `POST /internal/v1/permissions/check` for a collection decision, and `POST /internal/v1/scopes/page` for a paged role and scope read. Put identity information in request bodies rather than URLs. The scope operation is logically read-only; user resolution may write and must not be automatically retried under the existing retry policy. Detailed validation, status-to-code mappings, and transaction mechanics remain open.
- FR-34: Include a typed identity assertion in each internal operation's JSON body: the validated issuer and subject for OIDC, or the configured local namespace and authenticated username for local Basic. Reject missing, malformed, or unsupported identity types. Only the allowlisted backend asserts identities after authentication; these calls do not rely on browser-supplied identity headers and do not send passwords or bearer tokens. Local Basic remains development-only. Allowed issuers and namespace configuration remain open.
- FR-35: Resolution of an authenticated OIDC identity creates a missing user as `MEMBER` with no grants, without changing an existing user's role or grants. Resolution does not automatically create local users; an authenticated local identity without a policy record retains `NONE`, empty scopes, and denied protected access. First-time OIDC provisioning remains blocked during the migration write freeze.
- FR-36: Start with a configurable scope-page default of 100 entries and maximum of 500 entries. The backend may request a size up to the configured maximum; reject invalid or oversized requests rather than silently changing them. The 10,000-distinct-collection limit and total deadline still apply; measure large-scope behavior with integration and load tests.
- FR-37: Use these internal JSON field shapes, with collection IDs represented as UUID strings:
  - Identity: `{"kind":"OIDC","issuer":"…","subject":"…"}` or `{"kind":"LOCAL","namespace":"…","username":"…"}`.
  - User resolution: request `{identity}`; success `{status}`, where status is `EXISTING`, `CREATED`, or `NOT_FOUND`. Missing OIDC users are created subject to the write freeze; unknown local users return `NOT_FOUND`.
  - Permission check: request `{identity, collectionId, permission}` with `READ` or `MANAGE`; success `{decision}` with `ALLOW` or `DENY`.
  - Scope page: request `{identity, pageSize?, cursor?}`; success `{role, revision, entries, nextCursor}`. Role is `ADMIN`, `MEMBER`, or `NONE`; entries contain `{collectionId, permission}`; revision is an opaque string and `nextCursor` is a string or `null`.
  - Validation limits and key-management details remain open.
- FR-38: Internal error categories are `400` for malformed requests, unsupported values, or invalid cursors; `403` for a trusted certificate whose backend identity is not allowlisted; `409` for a changed pagination revision; `422` for exceeding the configured scope limit; and `503` when the auth service cannot safely perform the operation. Invalid TLS certificates may fail at the handshake without an HTTP response. Unexpected server errors remain errors, never decisions. On revision change, discard all pages and restart only within the approved deadline and retry limit. If Java cannot obtain a valid complete decision or scope, return the previously approved safe public 503 without internal details. Genuine `DENY` is a successful decision; existing public invalid-credential 401 and non-disclosing resource-denial 404 remain unchanged. Mappings are specified in FR-58.
- FR-39: Use deployment-managed cursor signing keys kept outside Git and logs. Sign with one active key and allow a bounded set of previous keys for verification during rotation, only long enough for valid cursors to expire accounting for clock skew. Start with a configurable 60-second maximum cursor lifetime. Reject expired, tampered, unsigned, or unknown-key cursors; missing or unusable key configuration fails closed. The existing authorization deadline remains in force. The selected algorithm is specified in FR-46; secret-management product and exact rotation procedure require security review.
- FR-40: Order scope entries by PostgreSQL's native UUID order and use keyset pagination. The signed cursor records the last returned collection ID; the next page begins strictly after that ID. Every page still checks the global revision and reads a consistent snapshot. Exact SQL and indexes remain to be designed.
- FR-41: A complete scope read shares one retry allowance: retry one failed, explicitly idempotent page request, or restart the complete read once after a revision change, but not both. All pages and the retry must fit within the configured total deadline. On exhaustion, discard the pages and return a safe 503. User resolution remains non-retried because it may write.
- FR-42: OIDC user resolution is idempotent at the data level: a unique issuer-and-subject identity permits at most one user record. Concurrent or later resolution of an existing identity must not change its role or grants. New users start as `MEMBER` with no grants, and first-time creation remains blocked during the migration write freeze. This does not authorize automatic retries of user resolution. Exact transaction and constraint mechanics require review.
- FR-43: Internal HTTP errors use a stable `code` and `correlationId`, without identity or policy data, stack traces, or raw request bodies. Selected codes are `INVALID_REQUEST`, `INVALID_CURSOR`, `CALLER_FORBIDDEN`, `POLICY_REVISION_CHANGED`, `SCOPE_LIMIT_EXCEEDED`, and `SERVICE_UNAVAILABLE`; TLS handshake failures may have no JSON response. When authorization cannot be obtained, the planned Java public 503 uses the existing error-envelope shape with code `AUTHORIZATION_SERVICE_UNAVAILABLE` and message `Authorization service is temporarily unavailable`. This is not yet implemented. Detailed validation limits remain open.
- FR-44: Independently check asserted OIDC issuers against a deployment-configured allowlist. Accept local identity assertions only in an explicitly configured local-development deployment and only for its configured local namespace; production must reject them. Invalid issuer or namespace assertions fail closed. Java remains responsible for authenticating the user before assertion; this does not approve additional issuers or multi-tenancy.
- FR-45: Enforce the migration write freeze using a database guard as well as application handling. The guard blocks policy writes, first-time provisioning, and scope-affecting collection changes from ordinary runtime roles. Applications detect the freeze and return a safe temporary error for blocked operations. An explicitly controlled migration role may perform only approved copy and reconciliation work. Before taking a snapshot, operators activate the freeze, drain or finish in-flight writes, and verify that the guard is active. The exact roles, guard mechanism, privileges, and recovery procedure require design, tests, and security review.
- FR-46: Sign continuation cursors using HMAC-SHA-256 and a dedicated, cryptographically random secret of at least 256 bits, securely shared among auth-service instances. Keep the key separate from other secrets and outside Git and logs; follow the approved verification-key overlap during rotation. Signatures do not encrypt cursor contents: do not include raw sensitive identity information, and design privacy-safe request binding for security review.
- FR-47: Use deployment-managed automatic issuance and renewal of backend client and auth-server certificates before expiry. Permit a controlled overlap of old and new valid certificates during routine rotation, then remove the old certificate. If renewal or validation fails, do not disable mTLS or accept expired certificates; affected calls fail closed. Local development retains a separate CA. Certificate provider, lifetime, compromise-response deadlines, and exact rotation procedures require review.
- FR-48: The backend connects to a deployment-configured auth-service hostname and verifies that the auth-server certificate chains to its configured trusted CA and matches that hostname using a DNS SAN. Reject expired, untrusted, or hostname-mismatched certificates. Do not bypass hostname verification in production; local development uses its separate CA and a matching local hostname. Backend client authentication remains mandatory.
- FR-49: Initially use end-to-end mTLS from Java to the auth service; the auth service validates the backend client certificate itself and checks its URI SAN against the configured allowlist. A network proxy may pass encrypted traffic through but must not terminate this TLS connection or supply backend identity in an HTTP header. A change to this trust boundary requires separate design and approval.
- FR-50: On cursor-signing key compromise, immediately remove the key from signing and verification across all auth-service instances, replace it, and reject cursors signed by it; routine verification-key overlap must not retain a compromised key. In-progress reads using those cursors discard partial pages and fail closed, and may start a fresh read only within the approved deadline and retry budget. The incident procedure must verify propagation to every instance and account for propagation delay.
- FR-51: Recheck authorization for every protected source included in model context, not only sources in final citations. On a genuine denial before provider submission, do not send the affected protected context. On a denial after submission but before returning the response, discard the entire generated answer and its citations; do not merely remove the denied citation. Failed or unavailable checks fail closed with the previously approved safe 503. Data already sent to a provider cannot be recalled.
- FR-52: For a genuine mid-request chat authorization denial, return a generic `403 FORBIDDEN` with message `Request cannot be completed`, without source, collection, or existence details, answer, or citations. Do not represent the denial as insufficient evidence. Unavailable or invalid authorization checks retain the safe 503, and document-specific denials retain non-disclosing 404. Coordinated public-contract and UI changes are required.
- FR-53: Apply the configurable two-second total authorization deadline to each authorization checkpoint: all auth-service calls and permitted retries needed to complete that checkpoint share its deadline. A later checkpoint gets a fresh deadline and fresh policy information. Existing retry limits and fail-closed timeout behavior remain in force. The overall chat-request timeout is a separate open decision.
- FR-54: Do not automatically rerun chat after a genuine mid-request authorization denial. A user-initiated new request must authenticate and authorize afresh and must not reuse protected context or the discarded answer. This does not change the approved limited retries for idempotent auth-service reads.
- FR-55: For urgent revocation during a migration or rollback freeze, stop the migration or rollback, block protected operations that cannot be safely authorized, and keep the current authority unchanged. Restore policy writes only to that authority under a controlled procedure, then apply and verify the revocation there. Invalidate the snapshot and reconciliation; a later attempt requires a new freeze, snapshot, and reconciliation. The detailed procedure and operator access require security review.
- FR-56: Document a local-development setup that creates a development-only CA and issues separate auth-server and backend-client certificates. Keep private keys outside Git; Java verifies the local server hostname and the auth service validates the backend URI SAN. Production must not trust the local CA or certificates. Exact commands, hostnames, file locations, and tooling remain to be designed; no unauthenticated transport fallback is permitted.
- FR-57: Bind the cursor to caller, user, query, and revision using a keyed digest of their canonical representation rather than raw user identity fields. Recompute and compare the digest on each page and reject mismatches. Use a binding key separated from the cursor-signing key and do not log cursors or their contents. Key derivation, canonical encoding, rotation behavior, and comparison require security review. A keyed digest is not encryption and can reveal equality between repeated values.
- FR-58: Map internal errors as follows: `400 INVALID_REQUEST` for invalid JSON, identity, permission, page size, or collection ID; `400 INVALID_CURSOR` for an expired, tampered, unknown-key, or request-mismatched cursor; `403 CALLER_FORBIDDEN` for a trusted client certificate with an unallowlisted identity; `409 POLICY_REVISION_CHANGED` for a valid cursor with an outdated policy revision; `422 SCOPE_LIMIT_EXCEEDED` for exceeding the configured scope limit; and `503 SERVICE_UNAVAILABLE` when the operation cannot safely be performed, including a write blocked by the migration freeze. Validate cursor binding using its authenticated revision before comparing that revision with the current database snapshot. TLS may fail before HTTP. Unexpected internal failures are specified in FR-59.
- FR-59: Return internal `500 INTERNAL_ERROR` for an unexpected auth-service failure using the safe `{code, correlationId}` envelope, without stack traces, identities, policy data, request bodies, or credentials. Java treats it as an inability to obtain authorization and returns the approved public `503 AUTHORIZATION_SERVICE_UNAVAILABLE`. Safe operational logs may include the correlation ID and a non-sensitive failure category; detailed logging rules require review.
- FR-60: Represent the global revision internally as an epoch and monotonic counter, while keeping it opaque to API consumers. Scope-affecting transactions increment the counter; a controlled restore or reinitialization changes the epoch before authorization traffic resumes so old revisions and cursors cannot become valid again. Guard and trigger atomicity, overflow handling, and the restore procedure require design and tests.
- FR-61: Use a reviewed migration mapping manifest for existing policy records. An authorized operator records each target identity type and issuer/subject or local namespace/username, supported by trusted deployment or identity-provider evidence. Validate that mappings are complete and unambiguous; protect the manifest as sensitive operational data and keep it out of Git and logs. A missing or ambiguous mapping stops migration; reconciliation verifies every role and grant. Format, evidence source, reviewer, and secure storage require further review.
- FR-62: Separate non-superuser auth runtime, schema-migration, and controlled data-migration database roles. Limit runtime access to required policy reads, first-time OIDC provisioning, and collection-ID reads; deny runtime DDL and direct privileges to disable guards or triggers. Limit migration roles to required schema or frozen-copy work. Design and test exact grants, trigger privileges, cascades, and collection lifecycle.
- FR-63: Guard and trigger privileges must be narrowly scoped and protected. Verify revision updates, consistent snapshots, the write freeze, and cascading deletion under concurrency. Revision overflow or inability to enforce the guard fails closed; specify the exact database mechanism before security review.
- FR-64: Operations must provide certificate expiry alerts and documented routine rotation. For server-certificate compromise, remove trust in the compromised certificate or issuer as appropriate, replace it, and verify backend rejection before resuming. Define the certificate provider, operational owners, certificate lifetime, measurable incident-response deadlines, and procedures before deployment.
- FR-65: Use deployment-managed secret storage with separate cursor signing and binding keys and least-privilege access. Use separate development-only keys locally. Document routine rotation, compromise response and propagation verification; choose the provider, key lifecycle, encoding, and procedures before deployment. Keep secrets out of Git and logs.
- FR-66: Forward migration requires a nominated operator and independent reviewer, verified backup and restore, an activated and verified freeze with drained writes, a consistent snapshot, a reviewed mapping manifest, and complete reconciliation of identities, roles, grants, and collection references. Rehearse rollback and retain Java as authority until separately approved cutover. Abort on mismatches; handle emergency revocation under FR-55.
- FR-67: Rollback freezes and drains writes, snapshots the current authority, and reverse-maps and reconciles every post-cutover change. Switch authority only after zero unresolved mismatches and explicit operational approval; verify enforcement before resuming writes. Conflicts block rollback, except for the controlled emergency abort. Restores change the revision epoch before traffic resumes; preserve and test forward-only migration history.
- FR-68: Define bounded UTF-8 identity fields and request/cursor sizes compatible with existing identities and the configured Keycloak issuer. Reject missing, duplicate, malformed, unknown, or inconsistent fields without silent truncation. Enforce page and total scope limits, require complete revision-consistent results, and validate every response; invalid or incomplete authorization fails closed. Establish and document numeric limits against current data and tests before implementation.
- FR-69: Inventory and test authorization checkpoints for document operations, retrieval, model context, answers, and citations. Preserve the existing `/api/v1/me` subject, role and complete scopes, subject to the selected scope limit, and coordinate the approved planned chat 403 and authorization-service 503 changes. Continue fresh server-side authorization without a decision cache.
- FR-70: Explicitly configure the currently approved Keycloak issuer and expected backend audience, match the issuer exactly, and configure the auth-service issuer allowlist. Local Basic assertions remain local-development only with a separate namespace and CA. Additional issuers and multi-tenancy are not approved.
- FR-71: Retain required audit behavior and ownership until an explicit transition is designed; do not silently drop mandatory audit records. Operational logs may contain correlation IDs and safe failure categories but not credentials, tokens, document text, request bodies, raw cursors, or sensitive policy data. Define ownership, retention and failure handling before cutover; expanded event types remain deferred.
- FR-72: The owner removed the requirement for an independent human security and architecture review before implementation. The review remains uncompleted; do not claim that a reviewer, scope, findings or evidence have been established. Production cutover still requires separate approval and the applicable security, migration and operational verification.
- FR-73: For reverse reconciliation under freeze, use a distinct restricted reverse-migration identity, separate from the forward data-migration and runtime identities. Permit only the reviewed old-policy operations needed for an approved rollback; ordinary writes and collection changes remain blocked. Define and review exact privileges, row scope, controls and operational procedures before using the migration mechanism.
- FR-74: Record privileged forward and reverse migration operations in a protected database-backed audit mechanism. A failure to record a required audit event must abort the corresponding migration operation rather than silently proceeding. Define and review event coverage, failed-attempt reporting, privacy, access, integrity, retention and operational ownership; do not log sensitive policy data.
- FR-75: Restrict forward and reverse migration changes to a protected, reviewed migration manifest using database-enforced procedures. Migration identities must not have direct policy-table write privileges that bypass the manifest check. Design and review manifest authorization, operation/value matching, privileges, lifecycle and reconciliation before implementation.
- FR-76: Report failed or rolled-back privileged migration attempts through an independently protected operational audit/log channel and alert operators without exposing sensitive policy data. Define and review delivery, failure reporting, ownership, retention and reconciliation with committed database audit records; failure to report must not turn a failed migration into a success.
- FR-77: For each migration or rollback run, activate a protected, independently reviewed manifest. Database procedures must match direction, operation, identity and expected old and new values against its entries, reject mismatches and replay, and enforce the freeze and restricted migration identity. Define atomic consumption, concurrent execution, cascades and recovery before implementation.
- FR-78: If the independent failure-alert channel is unavailable or cannot confirm delivery, stop the migration and surface an explicit operator error. Reconcile ambiguous outcomes against committed database audit and policy state before retrying; do not assume a timed-out transaction rolled back.
- FR-79: Initially use the validation and cursor defaults in [design-review section 12](./design-review.md#12-concrete-contract-and-cursor-proposals) only after verifying compatibility with existing identity data and configured issuers. Bind continuation to the original page size; reject explicit null cursor and malformed inputs. A missing OIDC identity after resolution is a service error, not an implicit authorization decision. If compatibility fails, stop and revise rather than truncate.
- FR-80: During the legacy-authority freeze, preserve read-only access for existing authenticated OIDC users when fresh authorization is available. The current Java provisioning filter attempts an `INSERT ... ON CONFLICT DO NOTHING` even for existing users; a statement-level freeze trigger rejects that attempt. The integration must avoid that write attempt for an existing user while retaining an atomic guarded first-time creation path. A concurrent create or freeze must never bypass the guard; a genuinely new user receives the selected safe temporary failure.
- FR-81: Preserve the existing public `/actuator/health/**` authentication exemption and keep unauthenticated health checks independent of policy resolution. Preserve the existing local-only Basic versus OIDC profile selection, including disabling Basic when `oidc` is active, and the incompatibility of `local` with `deployed`.
- FR-82: Carry the authenticated typed identity (OIDC issuer and subject or local namespace and username) through backend authorization checkpoints, rather than reconstructing it from a bare subject string. Preserve the existing public subject and document upload/deletion and lifecycle audit actor values; do not silently rewrite historical attribution or add authorization based on those actor fields.
- FR-83: Ensure authorization denials and authorization-service failures at every chat checkpoint cannot be converted into CRAG baseline fallback, external-search fallback, insufficient-evidence success, or a generated answer. Preserve the selected generic chat denial and safe 503 behavior, including errors propagated through asynchronous stage calls.
- FR-84: Map provisioning or authorization-service failures occurring in the Spring Security filter chain to the selected safe public 503 envelope and correlation ID, without assuming MVC controller advice handles filter exceptions. Preserve the existing authentication-failure 401 and never continue the filter chain as though authorization succeeded.

## 4. Security and non-functional requirements

- Authenticate and authorize service-to-service callers; client-supplied identity headers or permission lists must not be trusted without an approved verification mechanism.
- Specify secure transport, credential rotation, timeout and retry budgets, least-privilege storage access, observability and safe error mapping before implementation.
- Specify consistency and revocation behavior, including stale data, in-flight operations, concurrency, and outage handling; do not silently serve indefinitely cached grants.
- No passwords, tokens, document text, or confidential policy data in source control or logs. Preserve content-free security auditing as required by the approved requirements.
- Prefer a cross-schema foreign key from grants to backend-owned collections. The chosen schema ownership, transport, mTLS and foreign-key directions do not settle physical migrations, access privileges, deletion lifecycle, service identity or certificate handling; specify, test and review these details as applicable before use.
