# 013 Auth Service - Detailed Design Review Package

**Status:** Draft based on [spec.md](./spec.md) and [DEC-013](../../docs/implementation/product-decisions.md). Additional design details are proposals, not approved decisions. Independent review is not required before implementation and has not been completed;

## 1. Baseline, boundaries, and gates

- **Today:** Java validates Keycloak tokens, provisions users and enforces access; it remains authoritative until cutover. Local Basic is for development only. The existing [public API](../001-project-foundation/api-contract.md) remains in force; planned chat 403 and auth-unavailable 503 responses are not implemented.
- **Target:** Go owns identities, roles, grants and policy decisions, accepting assertions only from allowlisted backend clients over mTLS. Java remains responsible for authentication and protected-resource enforcement; Keycloak and browser sessions stay in place.
- **Progress:** Initial Go components, a loopback-only synthetic test server and an isolated guarded-schema candidate exist, but there is no deployment-ready service or verified migration. Tests cover a non-superuser installer and non-login owner, legacy and auth-table freeze/drain, revision overflow, cascading deletion, a restricted runtime login, fail-closed startup schema verification and frozen restore-epoch replacement. The candidate does not supply production ownership or migration controls. A read-only compatibility checker exists, but actual identity data and mappings have not been verified. A02 design, SQL and procedures remain incomplete; A03 tracks build and CI setup. Containers or VMs are the intended deployment direction, but the platform, providers and operational owners are undecided.
- **Before cutover:** Complete live Keycloak and cross-service testing, migration and rollback rehearsals, and operational readiness. Obtain separate cutover approval; do not remove existing protections beforehand.

## 2. Trust model and threats

**Trust boundaries:** Browser to Java (untrusted client, authenticated per current rules); Java to Go (direct mTLS and asserted identity); Go to PostgreSQL (separate restricted roles); deployment platform to services (certificate and key provisioning); migration operator to both policy stores (controlled elevated authority).

| Threat or failure                            | Required control                                                                                                                                                                                                           | Review and evidence                                                                                           |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Forged caller or identity                    | Java authenticates the user; Go validates client chain, expiry, and allowlisted URI SAN and independently restricts issuer/local namespace. No identity headers, passwords, or bearer tokens are accepted as caller proof. | mTLS, forged-header, wrong-issuer and wrong-profile tests.                                                    |
| Cursor tampering, replay, or mixed pages     | Authenticated, expiring cursor bound to caller, user, query, and revision; consistent snapshot and transactional revision update.                                                                                          | Tamper, binding, concurrency, restart and restore tests.                                                      |
| Revoked data leaks                           | Fresh access checks before protected retrieval, provider context, and returned content; check all context sources, including uncited ones.                                                                                 | Cross-service revocation tests; point-in-time race remains accepted and already-sent data cannot be recalled. |
| Unavailable or malformed policy              | Never allow, cache stale decisions, truncate scopes, or present an error as insufficient evidence.                                                                                                                         | Timeout, malformed response, over-limit, partial result and safe 503 tests.                                   |
| Write bypass during freeze or trigger bypass | Least-privilege roles, database guard, transactionally coupled revision, controlled migration authority, drain and verification.                                                                                           | Privilege and concurrent-write tests, including cascades and privileged operational paths.                    |
| Incorrect identity mapping or rollback       | Evidence-backed mapping, freeze, full reconciliation, controlled authority switch, reverse reconciliation.                                                                                                                 | Independent review and rehearsals with missing, ambiguous, conflicting and post-cutover records.              |
| Compromised certificate or cursor key        | Block affected identity/key, terminate connections as applicable, replace securely, verify propagation, and fail closed.                                                                                                   | Incident rehearsals and measured propagation times before deployment.                                         |
| Exposed secrets or policy                    | Restrict transport, storage and logs; never log tokens, passwords, raw cursors, request bodies, or protected document text.                                                                                                | Log inspection and access-control tests.                                                                      |

This model assumes the allowlisted backend and database administrators can assert or change powerful state. Their compromise is not prevented by mTLS alone. Access controls, privileged-write auditing, separation of duties and incident response need human review.

## 3. Proposed internal API contract

All three endpoints are `POST`, JSON, and backend-only. Proposed success status is `200`; all requests use a bounded UTF-8 JSON object and `Content-Type: application/json`. Correlation IDs follow the existing public contract's `[A-Za-z0-9._-]{1,64}` rule: propose the backend propagate a validated `X-Correlation-Id`, with the service generating one if absent or invalid; never include identity in it. The error body is `{ "code": "...", "correlationId": "..." }`. Reject duplicate or unknown object members, invalid UTF-8, trailing JSON values, unsupported types, and fields invalid for the identity kind.

An identity is either `{"kind":"OIDC","issuer":"<validated issuer>","subject":"<token sub>"}` or `{"kind":"LOCAL","namespace":"<configured local namespace>","username":"<authenticated username>"}`. Issuer and subject comparison must be exact; do not normalize, trim, case-fold, or substitute user-controlled strings. The owner selected the section 12 initial identity, request-body and cursor limits conditional on compatibility verification: measure existing persisted subjects and issuer configuration and obtain review before implementation. Reject oversize inputs rather than truncate them.

| Endpoint                         | Request                                                                           | Proposed success semantics                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/internal/v1/users/resolve`     | `{ "identity": ... }`                                                             | `{ "status": "CREATED" }` for a new OIDC `MEMBER` with no grants, `EXISTING` for an existing identity, `NOT_FOUND` for an unprovisioned local identity. Creation is atomic and unique per issuer/subject; existing role/grants are unchanged. During freeze first-time OIDC creation fails, but existing identities resolve. Do not automatically retry.                                       |
| `/internal/v1/permissions/check` | `{ "identity": ..., "collectionId": "<UUID>", "permission": "READ" \| "MANAGE" }` | `{ "decision": "ALLOW" \| "DENY" }` only after successful evaluation. `MANAGE` includes `READ`; `ADMIN` has both permissions. Unknown local identity denies; a missing OIDC identity after resolution is a service error under FR-79. Java still verifies the actual resource and its collection.                                                                                              |
| `/internal/v1/scopes/page`       | `{ "identity": ..., "pageSize": 100, "cursor": "<optional opaque cursor>" }`      | `{ "role": "MEMBER", "revision": "<opaque>", "entries": [{"collectionId":"<UUID>","permission":"READ"}], "nextCursor": null }`. Role is `ADMIN`, `MEMBER`, or `NONE`; each collection appears once in PostgreSQL UUID order, and `MANAGE` implies readable. `ADMIN` entries cover all collections. Unknown local identity has `NONE` and an empty list. A null cursor indicates the last page. |

The page-size default is 100 and initial maximum 500, both configurable; invalid sizes fail, not clamp. An omitted first-page cursor starts a new read; explicit null is rejected. Bind page size and endpoint/version as part of the cursor's query, and require the same size for continuation. Unknown response fields and enum values must not silently become valid decisions.

| Internal status and code      | Meaning                                                                                             |
| ----------------------------- | --------------------------------------------------------------------------------------------------- |
| `400 INVALID_REQUEST`         | Invalid request, identity, UUID, permission, or page size.                                          |
| `400 INVALID_CURSOR`          | Invalid signature, malformed, expired, unknown key, or mismatched binding.                          |
| `403 CALLER_FORBIDDEN`        | Valid trusted client certificate, but URI SAN is not allowlisted. Invalid TLS can fail before HTTP. |
| `409 POLICY_REVISION_CHANGED` | Valid, bound cursor with an authenticated revision different from the current snapshot.             |
| `422 SCOPE_LIMIT_EXCEEDED`    | More than the configured maximum distinct collections.                                              |
| `503 SERVICE_UNAVAILABLE`     | Unable to perform safely, including a write blocked by freeze.                                      |
| `500 INTERNAL_ERROR`          | Unexpected failure, with safe error body only.                                                      |

Java treats invalid or unavailable decisions as a safe public `503 AUTHORIZATION_SERVICE_UNAVAILABLE`; user authentication failures remain 401 and resource denials remain non-disclosing 404. A genuine mid-request chat denial follows the separately selected generic 403, not insufficient evidence. These public changes remain planned.

### Complete scope read and deadline

Proposal: within each page's consistent snapshot, determine whether the complete distinct scope exceeds the configured limit, by counting at most `limit + 1`; return `422` rather than a partial scope if it does. Verify the count, role, revision, and page correspond to the same snapshot. This may be expensive, especially for `ADMIN`; load tests must show acceptable behavior at 10,000 and fail safely if the deadline expires. An implementation may optimize only if it preserves equivalent completeness and consistency.

Java buffers all pages, verifies revision, role, UUID ordering, uniqueness, valid permissions and termination, and publishes nothing until complete. It discards all pages on revision change or failure. One shared allowance permits either a single retry of an explicitly idempotent failed page **or** one whole-read restart on `409`, not both. All calls and retries within an authorization checkpoint share the configurable two-second deadline. Later checkpoints use fresh policy and a fresh deadline; no authorization-decision cache is permitted. Independent permission-check retry mechanics and precise failure classification require review.

## 4. Proposed data model and database controls

Logical schema (physical identifiers and migrations require review):

| Object            | Proposed contents and invariants                                                                                                                                                                                                                                                                                                 |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `identities`      | Internal immutable ID, identity kind, issuer and subject **or** local namespace and username, role (`ADMIN`/`MEMBER`), optional existing display name, creation time. Exactly one kind's fields is present. Unique constraints on the exact OIDC pair and exact local pair; consider collation explicitly. No password or token. |
| `grants`          | `(identity_id, collection_id)` unique, permission `READ` or `MANAGE`; foreign keys to auth-owned identities and backend-owned `collections(id)`, with selected cascading grant deletion.                                                                                                                                         |
| `policy_revision` | One protected epoch/counter record. Changes to roles, grants, or collection membership affecting scopes increment it in the same transaction. The epoch changes before traffic resumes after restore or reinitialization. Overflow or inability to update fails closed, not wraps.                                               |
| `freeze_control`  | Protected freeze state and authority-transition controls; its exact representation and guarded-write mechanism require review.                                                                                                                                                                                                   |

Proposed role separation: a non-login owner for auth schema and narrowly scoped guard/trigger functions; separate non-superuser migration role for schema/trigger deployment; auth runtime gets only required schema usage, policy reads and safe identity provisioning plus `SELECT` on the backend's collection ID column; Java runtime retains resource access but cannot directly change auth policy or disable the guard; a separately controlled data-migration role gets only the privileges needed for reviewed copy/reconciliation under freeze. Exact grants, function execution rights, ownership, cross-schema `REFERENCES`, and the interaction with PostgreSQL cascades and existing Flyway ownership must be specified and tested rather than assumed. Do not give runtime ownership, superuser, `BYPASSRLS`, arbitrary function creation, or direct disable-trigger privileges. Administration API/UI remains deferred.

**Revision and freeze proposal:** guarded writer transactions coordinate with freeze control, then data changes and protected revision increments commit or roll back together. The freeze activator must prevent new writes from entering while waiting for already-admitted writes to commit or abort; only after confirming the guard is active and transactions are drained may it take the snapshot. Avoid trusting caller-controlled session variables as a bypass. Migration bypass, role membership, search paths and privileged functions require explicit review. Collection insertion/deletion must invalidate `ADMIN` scopes even without grants; cascading deletes must not evade revision or freeze checks. Define and test lock order to avoid deadlocks among freeze, revision, collection and grant operations.

For each page, propose a read-only PostgreSQL `REPEATABLE READ` transaction obtaining revision, role, limit check and page from a single snapshot. Validate the cursor signature and its binding against its **embedded authenticated revision** before comparing it to the snapshot revision; only a valid stale cursor gives 409. A consistent snapshot cannot prevent a policy change immediately after the final check. The selected guarantee is point-in-time, not instantaneous revocation.

Outstanding blocker: provide reviewed forward migration SQL and exact grant/function/lock design, including direct privileged writes, cascading deletes, concurrent freeze activation, rollback and restore. The above is a proposed invariant, not evidence that a specific trigger implementation is correct.

## 5. Cursor and operational security design

The service signs cursors with HMAC-SHA-256 and a dedicated random key of at least 256 bits. The proposed payload contains a format version, key identifier, issue/expiry time, authenticated revision, last UUID and a keyed binding digest; it contains no raw user identity. The digest covers an unambiguous canonical encoding of caller URI SAN, complete typed identity, endpoint/query parameters, page size and revision, using a distinct binding key. Encode with explicit field lengths and domain separation; do not concatenate ambiguous strings. Sign the entire encoded payload and compare authentication tags and binding digests in constant time. Signing and digest do not encrypt metadata, and the digest may reveal equality.

Start with configurable 60-second maximum lifetime, one active signing key, and bounded previous-key verification only while valid cursors can survive, accounting for an explicitly specified clock skew. Signing and binding key versions must be selected and retired together in a reviewed manner so legitimate in-flight cursors can be verified during normal rotation. Reject unknown, expired, malformed, unsigned, or tampered tokens; never log tokens or contents. Key identifiers, maximum cursor length, exact serialization, cryptographic derivation, expiry/clock semantics and simultaneous key rotation remain proposals for human review.

- **Normal certificate operations:** Platform issues client and server certificates, renews before expiry, alerts on expiry, stages controlled overlap, verifies new credentials across instances, drains old connections and removes old credentials. Java validates CA and server DNS SAN; Go validates the backend URI SAN. Local CA and secrets are separate and never trusted by production.
- **Client compromise:** Remove the URI SAN from all auth-service allowlists and terminate existing connections; fail closed. Restore with a new URI SAN and certificate while keeping the compromised identity blocked. Re-enable the old identity only after verifying the compromised certificate cannot authenticate. Document in-flight request handling and measure propagation.
- **Server compromise:** Remove trust in the affected certificate or issuer as appropriate, replace credentials, verify that Java rejects the compromised server and accepts the replacement, then restore service. Do not assume blocking a single certificate is possible with a CA-only trust configuration.
- **Cursor key compromise:** Remove the compromised key from signing and verification on every instance, replace it, verify propagation and reject its cursors. In-flight reads discard partial data and obey the existing deadline/retry budget. Do not use the normal overlap to retain a compromised key.

Provider selection, certificate lifetime, expiry-alert thresholds, trust-removal mechanism, propagation deadlines, access controls, secure storage, and named incident owners remain unresolved. The runtime must fail closed if required configuration cannot be validated; no unauthenticated transport fallback.

## 7. Draft migration, rollback, and incident runbooks

These are review sequences, **not executable commands or permission to operate on live data**. Name operator and independent reviewer, specify actual credentials, platform controls, verified backup/restore and stop conditions before approval.

### Forward migration and cutover

1. Inventory source records, all policy/collection writers, and current identity provenance without placing sensitive exports in Git or logs. Review an evidence-backed mapping for every source record. Missing or ambiguous mappings block migration.
2. Verify backups by restore rehearsal in an isolated environment, target schema and referential integrity, role privileges, freeze guard, revision triggers, and rollback procedure. Ensure the source remains sole policy authority.
3. Activate the guard, stop or drain in-flight affected writes, verify the guard and controlled migration access, then take a consistent snapshot. Existing users may read only when current authority can enforce fresh authorization; block provisioning and scope-affecting writes with safe temporary errors.
4. Copy mapped users and grants with the controlled migration role. Compare every mapped identity, role, grant, permission and collection reference in both directions; validate counts, duplicates, orphans and conflicts, not counts alone. Record only safe evidence. Any mismatch stops the switch.
5. Test target integration and live Keycloak behavior, rehearse rollback, verify security and operational gates, and obtain **separate explicit cutover approval**. Switch policy authority under freeze using a reviewed atomic deployment procedure; verify enforcement and one active writer authority before resuming writes. Exact switching and routing mechanics remain open.

### Rollback and urgent revocation

1. Freeze and drain writes on the current authority; snapshot current policy and prevent conflicting writers. Reverse-map and reconcile every post-cutover identity, role and grant with the former authority; never restore stale grants or silently merge identities.
2. On ambiguity, missing collections or mismatches, block the switch and keep writes frozen until resolved and reconciliation passes. Fail closed where access cannot safely be authorized. After explicit operational approval, switch authority, verify enforcement, then resume writes only on that authority.
3. If an urgent revocation cannot wait, invoke the approved emergency abort: stop migration/rollback, keep the current authority unchanged, block unsafe operations, restore writes **only** to it under controlled procedure, apply and verify revocation, discard the snapshot and reconciliation, and restart later from a new freeze.
4. After database restore or reinitialization, change the revision epoch and verify old cursors cannot be accepted before authorization traffic resumes. Preserve Flyway history; forward-only schema changes and any compensation require a reviewed deployment plan.

```sql
    identity_id uuid PRIMARY KEY,
    kind text NOT NULL CHECK (kind IN ('OIDC', 'LOCAL')),
    issuer text COLLATE "C",
    subject text COLLATE "C",
    local_namespace text COLLATE "C",
    username text COLLATE "C",
    role text NOT NULL CHECK (role IN ('ADMIN', 'MEMBER')),
    display_name text,
    created_at timestamptz NOT NULL,
    CHECK (
        (kind = 'OIDC' AND issuer IS NOT NULL AND issuer <> ''
         AND subject IS NOT NULL AND subject <> ''
         AND local_namespace IS NULL AND username IS NULL)
        OR
        (kind = 'LOCAL' AND local_namespace IS NOT NULL AND local_namespace <> ''
         AND username IS NOT NULL AND username <> ''
         AND issuer IS NULL AND subject IS NULL)
    )
);
CREATE UNIQUE INDEX identities_oidc_key
    ON eka_auth.identities (issuer, subject) WHERE kind = 'OIDC';
CREATE UNIQUE INDEX identities_local_key
    ON eka_auth.identities (local_namespace, username) WHERE kind = 'LOCAL';
CREATE TABLE eka_auth.grants (
    identity_id uuid NOT NULL REFERENCES eka_auth.identities(identity_id) ON DELETE CASCADE,
    collection_id uuid NOT NULL REFERENCES public.collections(id) ON DELETE CASCADE,
    permission text NOT NULL CHECK (permission IN ('READ', 'MANAGE')),
    PRIMARY KEY (identity_id, collection_id)
);
CREATE INDEX grants_collection_idx ON eka_auth.grants (collection_id);
CREATE TABLE eka_auth.control (
    singleton boolean PRIMARY KEY DEFAULT true CHECK (singleton),
    frozen boolean NOT NULL,
    epoch uuid NOT NULL,
    revision bigint NOT NULL CHECK (revision >= 0)
);
```

### 11.3 Guard and revision transaction protocol

Proposed transaction and trigger behavior; the linked prototype demonstrates only part of it and is not sufficient to close A02:

1. For each policy-affecting write on both the legacy authority and target policy tables, and collection changes, a `BEFORE STATEMENT` guard acquires a transaction-scoped shared advisory lock, then locks and verifies the singleton control row or rejects the write. Also cover `TRUNCATE` as denied or guarded; enumerate all permitted writers, including maintenance jobs and direct SQL.
2. The controlled freeze procedure obtains the exclusive advisory lock, waits for admitted writers to commit or abort, updates `frozen = true` and commits. New writers then observe the committed freeze or fail with a serialization error; timeouts or serialization failures are safe errors, never bypasses. Verify the freeze is active and earlier writes drained before taking the snapshot.
3. During freeze, a dedicated, auditable forward-migration login may copy to **target** tables only. A distinct reverse-migration identity may perform reviewed operations on the **old policy** tables for rollback; neither identity may bypass the collection freeze. Neither a client-supplied flag nor an untrusted session variable is a bypass. Review checks on actual login identity and role membership, and test that privileged functions cannot be called by runtime users.
4. An `AFTER STATEMENT` trigger increments the counter in the **same transaction** for affected role, grant and collection changes. A conservative increment for a no-op is acceptable; it may cause extra restarts. Cascaded grant deletion must fire the intended trigger or otherwise increment equivalently. A missing row, overflow, disabled or failed guard/trigger aborts the transaction and must fail closed. Epoch replacement after restore occurs while traffic is blocked.
5. A scope-page `REPEATABLE READ`, read-only transaction reads control revision, identity role, complete-scope limit and keyset page from one snapshot. Compare a verified cursor's embedded revision to that snapshot; return 409 on mismatch. The consumer discards all pages. No snapshot can revoke data already sent or eliminate the approved race after the final check.

The prototype acquires the shared advisory lock before taking an exclusive row lock on the control row; the revision trigger updates that row in the same transaction. The row lock serializes affected writers and may be a substantial throughput bottleneck. It also makes an old repeatable-read snapshot fail on a concurrently changed control row instead of admitting a write after freeze. There is no shared-to-exclusive advisory-lock upgrade. Locks already held on other rows, cascade paths and different multi-statement orders can still deadlock; PostgreSQL may abort a transaction. The application must fail closed, and an independent reviewer must validate lock ordering, performance and broader isolation/concurrency cases. These tests do **not** establish deadlock freedom.

### 11.5 Manifest and audit design for independent review

The owner selected the controls below as the direction for completing the design. The original guard prototype does **not** implement them; a separate, deliberately limited manifest prototype and its evidence are described in section 11.6.

1. A privileged preparation process creates a run-specific manifest in protected storage. Each entry identifies direction, operation, exact record identity and expected old/new values, including explicit absence where applicable. A distinct authorized reviewer checks mapping evidence and the complete entry set. A controlled activation procedure binds that review to an immutable manifest version and digest, run ID and direction; modifications invalidate activation. The reviewer must not be able to silently approve a different version. The precise representation and evidence mechanism must be implemented and independently reviewed.
2. The migration login has no direct write access to policy, manifest approval, control, audit or procedure definitions. It may invoke only the direction-specific procedure, supplying a run ID and entry ID. A non-login procedure owner has only the required table rights; `PUBLIC` execution and untrusted schema creation are revoked, object names are qualified and the search path pinned. Verify effective grants, inherited memberships, function ownership and session identity with actual connections, not just `SET ROLE`. Database owners and administrators remain privileged and require separate access controls and audit.
3. In one transaction, the procedure checks authenticated login, active freeze and matching activated run and direction; locks the entry and relevant policy rows in a documented order; compares the actual current record with the exact expected old state; applies only the entry's expected new state; marks the entry consumed; and records the committed-operation audit event. Missing, changed, inactive, already consumed or mismatched entries, unauthorized callers and database errors abort the entire transaction. Never accept caller-supplied policy values in place of reviewed manifest values. Unique constraints and locks must prevent concurrent duplicate execution.
4. Cascades and triggers must not introduce unreviewed changes: either explicitly represent and verify every affected grant in the same transaction or reject the operation. In particular, deleting an identity with cascading grants must not silently bypass manifest matching. Collection writes remain frozen in both directions. Reconciliation checks the complete final identity, role, grant and collection state, not just manifest consumption or counts. Activation, expiry, partial runs, abort, re-review and reactivation need explicit procedures and tests.
5. Append a privacy-safe committed-operation audit record in the same transaction, protected from runtime and migration-role modification. If the required record cannot be inserted, the policy change and consumption roll back. A separately protected operational channel records and alerts failed or rolled-back attempts without policy contents or secrets. Since transaction rollback erases transactional records, the operator-side process must report after observing failure and also handle lost connections and unknown commit outcomes.
6. If the independent channel cannot confirm delivery, stop the run and surface an explicit operator error; do not silently continue. A connection loss or timeout can leave the transaction outcome unknown: inspect committed audit, manifest consumption and policy state through authorized read-only reconciliation before retrying or reporting success. Define durable delivery acknowledgment, duplicate handling, crash recovery, channel outage escalation, audit retention and safe metadata with the eventual platform owner. Do not promise delivery while that channel is unavailable.

Required synthetic tests include both directions; insert/update/delete and cascades; wrong login, role membership, direct writes and `PUBLIC`; unreviewed, changed, inactive, wrong-direction, missing and replayed entries; old/new mismatches; concurrent consumption; audit-write failure; rollback; unknown commit outcome; alert failure; and attempts to bypass the freeze. Exact executable SQL, privilege setup and independent-channel implementation are still outstanding.

## 12. Concrete contract and cursor proposals

The owner selected these initial defaults conditional on compatibility verification and independent review. Before finalizing bounds, compare safe aggregate byte-length distributions and maximums from existing legacy records and configured issuers without exporting identities. If existing data exceeds a proposed bound, stop and revise it; never truncate, silently exclude, or transfer grants to a different identity.

| Input                                        | Proposed validation                                                                                                                                                                                                                            |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP request                                 | `application/json`, valid UTF-8, max 16 KiB raw body; exactly one JSON object, no duplicate or unknown members, nesting limited to the defined identity object.                                                                                |
| `issuer`, `subject`, `namespace`, `username` | Nonempty UTF-8, each at most 1,024 encoded bytes; exact byte-preserving match, no trimming, normalization or case folding. Verify issuer and local namespace against configuration. Reject control characters only after compatibility review. |
| `collectionId`                               | Canonical UUID string; parse as UUID, reject malformed or extra values.                                                                                                                                                                        |
| `pageSize`                                   | JSON integer 1 through configured maximum, initially 500; omitted defaults to 100. Reject null, fractions and oversized values.                                                                                                                |
| `cursor`                                     | Omit for first page; use the two unpadded base64url segments separated by a period described below, maximum 4 KiB encoded. Reject null, malformed, expired or unknown-key values.                                                              |
| Response                                     | Check required fields, known status/role/permission/decision values, non-null entry list, canonical UUIDs, revision equality, consistent role, strict ordering and uniqueness. A malformed response is never `ALLOW` or `DENY`.                |

For strict evolution the proposed v1 contract rejects unknown fields, so adding fields requires coordinated versioning rather than silently accepting them. Exact response-size limit and error codes for oversized bodies need contract review. Under FR-79, unknown OIDC identity after resolution produces an internal service failure, not an implicit `DENY`; verify its race semantics.

### Cursor wire proposal

- Token is `base64url(payload) + \".\" + base64url(tag)` with no padding; cap decoded sizes before allocation. The payload is a versioned, fixed-field, length-delimited binary encoding: version, bounded key-pair ID, issue and expiry timestamps, epoch UUID and counter, last collection UUID, and binding digest. Reject trailing bytes and unsupported versions.
- Compute binding digest with HMAC-SHA-256 and a distinct binding key over a domain-separated, length-prefixed encoding of client URI SAN, complete typed identity, endpoint version, page size and embedded revision. Sign the complete payload with the separate HMAC-SHA-256 signing key. Select only configured key-pair IDs; authenticate before trusting payload fields. Use constant-time digest comparisons.
- Proposed expiry: at most 60 seconds from issue time, with at most 5 seconds allowed clock skew. Reject future issue times beyond skew, expiry earlier than issue, excessive lifetimes and timestamp overflow. Rotation retains a prior signing/binding pair only through the maximum cursor lifetime plus skew; emergency compromise removes the affected pair immediately. Confirm skew and clock synchronization with operations.
- Cursor format and digest are readable metadata, not encryption. Never log the cursor. Verify binding against its embedded revision before comparing that revision with the current database snapshot, so a valid stale cursor maps to 409 and a tampered cursor to 400.

Review the proposed encoding, size caps, allowed skew, key rotation across instances, and denial-of-service limits. The existing two-second checkpoint budget and shared scope-read retry allowance remain unchanged.
