# 013 Authentication and Authorization Service Extraction — Plan

**Status:** Draft; owner selected the target boundary and initial design directions, but detailed design and cutover are not approved.
**Specification:** [spec.md](./spec.md)

## 1. Boundaries

Keycloak remains the OIDC identity provider. The planned Go service owns user provisioning, application roles and grants, and policy decisions. The React frontend remains a client and provides login/session UX. The Java knowledge backend validates the request identity and enforces decisions before any protected data or model context is accessed.

The approved initial direction is internal HTTPS/JSON permission checks and bounded collection-scope lists, with mTLS between the backend and auth service. An authorized backend asserts the user subject only after authenticating that user; browser assertions must not be trusted. Policy storage is an auth-owned schema in the existing PostgreSQL deployment, with separate least-privilege access and a preferred cross-schema foreign key to backend-owned collections.

Backend authorization is fresh per protected operation without an authorization-decision cache. Recheck before protected AI-provider context and before returning protected citations or content. These checks are snapshots, not a guarantee of instantaneous revocation; the remaining race guarantees and consistency mechanics require review.

Initially retain direct Keycloak PKCE browser sign-in, the Java `/api/v1/me` contract, and local Basic sign-in. Migration uses a single policy authority at each stage, reconciliation, a rollback rehearsal and separate cutover approval. New administration UI/API and expanded audit-event features are deferred; existing required audit behavior is retained.

This is a target architecture, not current behavior. No gateway, new credential format, specific policy engine, detailed service contract, certificate lifecycle, or migration mechanism has been approved.

### Further owner-selected directions

- Version internal JSON operations for provisioning, permission checks and paged scopes. The consumer must establish complete, consistent results and fail closed on limits rather than silently truncate access scopes.
- Only explicitly configured mTLS client identities may assert a subject after Java authenticates the user. Deployment manages CA and client/server certificates; support rotation and expiry rejection. Local development uses a separate CA and keys outside Git.
- Accept the remaining point-in-time race after the selected rechecks; document and test boundaries. Data sent before revocation cannot be recalled.
- Map auth-service timeout, unavailability or invalid responses to a safe 503; use a configurable two-second total deadline and at most one retry for explicitly idempotent reads.
- Separate migration/runtime database roles and retain cascading grant deletion through a cross-schema FK. Freeze policy writes during cutover and reconcile; rehearse rollback and reverse-reconcile post-cutover changes under a write freeze before restoring the old authority.
- For paged authorized scopes, return a global policy revision on the first page and atomically validate it on subsequent pages. Scope-affecting role, grant and collection lifecycle changes, including cascading grant deletion, invalidate ongoing reads for all users. Discard all pages on a mismatch; restart only within the existing deadline and retry limit, otherwise fail with a safe 503. Start a fresh read for each protected operation.
- Start with a configurable limit of 10,000 distinct authorized collection IDs per user across readable and manageable scopes, counting IDs present in both only once. Exceeding the limit fails closed with a safe 503, not a truncated scope.
- Use separate internal operations for user provisioning or resolution, a collection permission check, and reading the user's role and paged collection scopes. Selected paths, field shapes, pagination and error categories are specified below; remaining contract details require review.
- Return one scope entry per authorized collection with its effective `READ` or `MANAGE` permission, plus role, global revision and a continuation cursor when more pages exist. Java reconstructs the existing `/api/v1/me` lists; `MANAGE` implies `READ`, and `ADMIN` scopes include all applicable collections subject to the limit.
- Successful permission evaluations return explicit `ALLOW` or `DENY`; malformed or failed evaluations are errors and fail closed. Denials for protected resources remain non-disclosing 404s. Java independently establishes resource existence and collection ownership; `ALLOW` alone does not do so.
- Use stateless integrity-protected continuation cursors bound to the authenticated caller, asserted user, query and global revision. Verify each cursor and independently check the current revision atomically; reject invalid or mismatched cursors. Cursors are not authorization caches, and signing does not encrypt their contents.
- Maintain the global revision in PostgreSQL with triggers on scope-affecting role, grant and collection changes, including cascading grant deletion. The change and revision update commit or roll back together; read each page's revision, role and scope data from one consistent snapshot. Trigger privileges, migrations, concurrency and lifecycle mechanics remain subject to security review.
- Authenticate backend client certificates and authorize their URI SAN by exact match against a deployment-configured allowlist. The backend validates the auth server certificate and expected server identity. Issuance, revocation and local setup remain open.
- Distinguish OIDC identities by validated issuer and subject and local identities by a separately configured local namespace and username. Preserve the public `/api/v1/me` subject and require verified migration mappings; ambiguous mappings stop migration without silently merging accounts or transferring grants. This does not approve additional issuers or multi-tenancy.
- Use freeze-and-copy migration with a consistent users/grants snapshot, explicit identity mapping and full role/grant reconciliation. Stop on ambiguous mappings, missing collections, conflicts or mismatches. Java stays authoritative until verification and separate cutover approval; resume policy writes only after a single authority is established. The runbook, rollback and outage plan remain open.
- During the migration freeze, block first-time user provisioning, policy writes, and scope-affecting collection changes. Existing authenticated users may continue read-only access only while the current authority can enforce fresh authorization; otherwise fail closed. Blocked writes receive a safe temporary service-unavailable response without partial changes. Exact operations and messages remain open.
- Initially respond to a compromised backend client certificate by removing its URI SAN from the allowlist and terminating existing connections for that identity. This blocks all certificates sharing the identity. Restore service with a new URI SAN and certificate while keeping the compromised identity blocked; re-enable the old identity only after separately verifying the compromised certificate cannot authenticate. Lifetimes, propagation deadlines, in-flight requests, the procedure and server-certificate compromise handling remain open.
- Block rollback on identity collisions, unmappable users, missing collections, or role/grant mismatches. Keep policy writes frozen, resolve conflicts and rerun reverse reconciliation before switching authority, except when invoking the controlled emergency abort described below. Fail closed when operations cannot be safely authorized; do not drop or broaden grants to complete rollback.
- Give the auth runtime database role read-only access to the backend-owned collection ID column for complete `ADMIN` scopes, not document content or other collection fields. Keep migration privileges separate; exact grants, trigger privileges and ownership require security review.
- Use backend-only `POST /internal/v1/users/resolve`, `POST /internal/v1/permissions/check`, and `POST /internal/v1/scopes/page` with identity information in request bodies. Scope pages are logically read-only; user resolution may write and must not be automatically retried under the current retry policy. Detailed validation and transaction mechanics remain open.
- Each operation carries a typed identity assertion: validated issuer and subject for OIDC, or configured local namespace and authenticated username for local Basic. Reject malformed or unsupported assertions and untrusted callers; do not send passwords or bearer tokens. Issuer and namespace configuration remain open.
- Preserve existing user resolution: provision missing OIDC users as `MEMBER` without grants and do not change existing roles or grants; do not automatically provision local users. An unknown local user retains `NONE`, empty scopes and denied protected access. First-time OIDC provisioning remains blocked during the migration freeze.
- Start with a configurable scope-page default of 100 entries and maximum of 500; reject invalid or oversized requests. Retain the total scope limit and deadline, and measure large-scope behavior with integration and load tests.
- The selected internal JSON shapes are in FR-37 of the specification; validation limits and key-management details remain open.
- The selected internal HTTP error categories and status-to-code mappings are in FR-38, FR-58 and FR-59. Java maps inability to obtain a valid complete decision or scope to a safe public 503, retaining existing public invalid-credential 401 and non-disclosing resource-denial 404 behavior.
- Sign cursors with deployment-managed keys outside Git and logs; start with a configurable 60-second maximum lifetime and bounded previous-key verification overlap accounting for clock skew. Reject expired, tampered, unsigned or unknown-key cursors and fail closed on unusable key configuration. Use HMAC-SHA-256 with a dedicated cryptographically random secret of at least 256 bits securely shared among auth-service instances. Cursor contents are not encrypted; privacy-safe request binding, secret-management product and rotation procedure remain open for security review.
- Use PostgreSQL native UUID order and keyset pagination, with the last returned collection ID in the signed cursor. Each page still checks the revision and reads a consistent snapshot. Exact SQL and indexes remain open.
- A complete scope read shares one retry allowance: retry one explicitly idempotent failed page or restart once after a revision change, not both. All pages and the retry must fit the configured total deadline; otherwise discard partial pages and return a safe 503. User resolution remains non-retried.
- OIDC resolution is idempotent at the data level with a unique issuer-and-subject identity. Concurrent or later resolution must not alter existing roles or grants; the write freeze blocks first-time creation. This does not authorize automatic retries. Exact transaction and constraint mechanics remain open.
- Use the stable internal error codes and safe envelopes in FR-43 and mappings in FR-58 and FR-59. The planned Java public 503 uses `AUTHORIZATION_SERVICE_UNAVAILABLE`; this is not yet implemented. Validation limits remain open.
- Independently allowlist asserted OIDC issuers; accept local assertions only in an explicitly configured local-development deployment for its configured local namespace, never in production. Java still authenticates each user first. This does not approve additional issuers or multi-tenancy.
- Enforce the migration write freeze with a database guard and application handling. Block affected writes from ordinary runtime roles, limit a controlled migration role to approved copy and reconciliation work, and verify the freeze and drain or finish in-flight writes before the snapshot. Exact roles, guard mechanism, privileges and recovery procedures remain subject to design, tests and security review.
- Use deployment-managed automatic issuance and renewal of mTLS certificates before expiry, with controlled overlap during routine rotation and removal of the old certificate. Failed renewal or validation must fail closed without disabling mTLS or accepting expired certificates. Provider, lifetime, compromise-response deadlines and exact procedures remain open.
- The backend validates the auth-server certificate against its trusted CA and the deployment-configured hostname via a DNS SAN. Reject expired, untrusted or hostname-mismatched certificates without a production hostname-verification bypass. Local development uses its separate CA and a matching hostname.
- Initially terminate backend-to-auth mTLS at the auth service itself, which validates the client certificate and allowlisted URI SAN. A proxy may pass encrypted traffic through but may not terminate TLS or supply the backend identity in an HTTP header; changing this trust boundary requires separate design and approval.
- On cursor-key compromise, immediately remove the key from signing and verification across all auth-service instances, replace it and reject its cursors rather than retaining it for routine overlap. Discard partial reads and fail closed; a fresh read is allowed only within the approved deadline and retry budget. Verify propagation to every instance and account for delay in the incident procedure.
- Recheck all protected model-context sources, not only final citations. A pre-submission denial prevents sending affected context; a denial after submission but before the response discards the entire generated answer and citations. Return a generic `403 FORBIDDEN` without source or existence details for a genuine mid-request chat denial, not insufficient evidence; failed checks return a safe 503. Coordinate public-contract and UI changes. Do not automatically rerun chat after a genuine denial; a user-initiated new request authenticates and authorizes afresh without reusing protected context or the discarded answer. Provider data already sent cannot be recalled.
- Apply the configurable two-second authorization deadline to each checkpoint, shared by all its auth-service calls and permitted retries. Later checkpoints get a fresh deadline and fresh policy information. The overall chat-request timeout remains a separate open decision.
- For urgent revocation during a migration or rollback freeze, stop the operation, block protected operations that cannot be safely authorized, and keep the current authority unchanged. Restore writes only to that authority under a controlled procedure and apply and verify the revocation. Discard the snapshot and reconciliation; a later attempt requires a new freeze, snapshot and reconciliation. Operator access and detailed procedures remain subject to security review.
- Document a separate local-development CA issuing server and backend-client certificates. Keep private keys outside Git, validate server hostname and client URI SAN, and prevent production from trusting the local CA or certificates. Exact commands, hostnames, locations and tooling remain open; no unauthenticated transport fallback is permitted.
- Bind cursors to caller, user, query and revision using a keyed digest of their canonical representation rather than raw user identity fields. Recompute it on each page using a key separated from the signing key; do not log cursors or their contents. Key derivation, encoding, rotation and comparison require security review; the digest can reveal equality and does not encrypt.
- Represent the global revision as an epoch and monotonic counter, opaque to API consumers. Scope-affecting transactions increment the counter; change the epoch before authorization traffic resumes after restore or reinitialization so old cursors cannot become valid again. Guard and trigger atomicity, overflow handling and restore procedure remain open.
- Use a reviewed, evidence-backed migration mapping manifest for every existing policy record, identifying the target OIDC or local identity. Validate completeness and ambiguity; stop on missing or ambiguous mappings and reconcile every role and grant. Protect the manifest and keep it out of Git and logs. Format, evidence, reviewer and secure storage remain open.

### Consolidated review directions

The owner selected the following directions; they are not a completed detailed design or security review:

- Separate non-superuser runtime, schema-migration and controlled data-migration roles, with least-privilege policy and collection-ID access. Runtime cannot perform DDL or directly disable guards and triggers. Specify and test grants, trigger ownership, cascades, concurrent snapshots, freeze enforcement and fail-closed overflow.
- Use managed certificates and secrets, expiry alerts, controlled rotation, separate development keys and least-privilege access. Document client, server and key compromise procedures, including trust removal and verified propagation. Providers, operational owners, lifetimes and measurable incident deadlines remain undecided.
- Document forward and reverse migration runbooks with a named operator and independent reviewer, verified backup and restore, freeze and drain, evidence-backed mapping, complete reconciliation, rollback rehearsal and post-switch enforcement checks. An authority switch requires separate approval; conflicts and emergency revocation follow the selected safeguards.
- Specify strict bounded input validation against existing identities and issuer configuration, reject malformed, duplicate, unknown and inconsistent fields, and test complete, revision-consistent scopes. Inventory protected-operation checkpoints and preserve `/api/v1/me` while coordinating the planned chat 403 and authorization 503.
- Explicitly configure the approved Keycloak issuer and backend audience; restrict local identity and development CA use to local development. Preserve required audit behavior and ownership until a transition is designed, never silently drop mandatory records, and keep sensitive data out of operational logs.
- Obtain documented independent human security and architecture review of the complete contract, threat model, database grants and SQL, certificate and key operations, migration/rollback and test strategy before design approval and implementation. Unresolved high-risk issues block approval; reviewer and platform are not yet identified.
- For A03, propose Go module path `github.com/kumarpramodlohar/enterprise-knowledge-auth`, standard Go formatting, tests and vet, and CI appropriate to the actual platform. Verify a supported Go version and document libraries, layout and CI before implementation; the installed local toolchain does not establish project support.

Endpoint validation limits, configured page-size rules and scope-limit enforcement, trigger and snapshot mechanics, privacy-safe cursor binding, secret management, rotation and error mapping, exact mTLS identity/certificate procedures, database grants, operation boundaries and migration runbook still need specification and security review. Owner selection does not complete A02.

## 3. Interfaces and data

- Current public contract: [foundation API contract](../001-project-foundation/api-contract.md), including `/api/v1/me` and safe 401/404 responses. Preserve it until an approved coordinated change.
- Selected service capabilities and internal paths, field shapes, pagination and error mappings are recorded above. Remaining validation, logging and contract details require review.
- Design service caller identity, message authentication, transport, timeout, fail-closed semantics, scope bounds, revocation freshness and the security of admin operations before an API contract is approved.
- Design how the auth service refers to backend-owned collection IDs and handles deletion/creation without orphaned or resurrected grants. Determine authoritative storage, ownership, permissions and forward-only schema migration.

## 4. Migration sequence

1. Resolve the open decisions in the specification; approve the contracts, threat model and migration/rollback plan. Open the new Go repository in the workspace.
2. Implement and test the Go service against representative local fixtures, without disabling the existing checks. Establish secure caller authentication and an authoritative policy data source.
3. Freeze policy writes and migrate/reconcile identity and grant data by the selected freeze-and-copy method under an approved cutover process. Define who can write during each phase, failure recovery, rollback and revocation handling; avoid unsynchronized dual authorities.
4. Integrate the Java backend and frontend as required. Keep identity validation and enforce authorization before content access. Validate cross-service failure and non-disclosure behavior.
5. Run contract, integration, migration, authorization and live Keycloak tests. Record results and cutover approval; only then remove superseded implementation and move operational ownership.

## 5. Test strategy

- Go unit and integration tests for provisioning, policy decisions, service authentication, role/grant semantics, safe failures, and persistence.
- Java integration tests for identity validation, every document lifecycle operation, readable scopes in RAG, citation access, unauthorized provider-context exclusion and auth-service failures.
- Frontend tests for login, callback, session expiry, sign-out, `/me` compatibility and permission affordances.
- End-to-end Keycloak tests, revocation/consistency tests, data reconciliation and rollback rehearsal. Do not claim completion based on mocks alone.
- Test role, grant and scope-affecting collection lifecycle changes, including cascading grant deletion, between scope pages; verify global invalidation, discarding mixed results, successful bounded restart, and safe failure when a consistent complete result cannot be obtained.
- Test the initial 10,000-distinct-collection boundary, overlap between readable and manageable scopes, rejection of 10,001 without partial results, and an alternative configured limit.
